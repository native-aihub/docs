Review decisions are separate from technical extraction `status`. A pending document can receive one final decision: approval, rejection, or expiry.

<Warning>
Explicit review decisions require the review-state migration and a compatible backend deployment. Documentation publication does not enable the feature. Check [review capabilities](/api-reference/review-capabilities) before integrating. Missing or unknown `review_status` must stop automatic processing; it is not approval. Rejection and expiry are disabled by default across the deployment until customer integrations support terminal decisions.
</Warning>

## Review in the web app

1. Open **Review** and select a pending document.
2. Correct extracted fields and choose **Save & Mark as Reviewed** to approve it.
3. If **Reject** is available, select it and choose a reason: Wrong document, Duplicate document, Out of scope, or Other.
4. Add a comment if the reason is Other. Comments accept up to 2000 characters.
5. Select **Reject document**, or select **Cancel** to return without a decision.

A rejected document leaves the pending queue and remains in History. History shows its decision state, actor identity, time, reason, and comment. Terminal documents are read-only. Rejection does not delete the document or refund credits. Documind records the decision; your connected process reads it and performs its own cancellation.

## Integration state contract

| `review_status` | Integration action |
| --- | --- |
| `pending` | Wait and poll again. |
| `approved` | Continue only when technical `status=completed`. Use `reviewed_results`; fall back to `results` only if reviewed results are null. An empty object is valid. |
| `rejected`, `expired` | Cancel your downstream work item. Your integration performs cancellation. |
| `not_required` | Use `results` only when technical `status` is `completed`. |
| `legacy_reviewed` | Preserve your existing legacy policy. This is not a new explicit approval. |
| Missing or unknown | Stop automatic processing and check deployment compatibility. |

Approved, rejected, expired, and legacy-reviewed records cannot be reopened or overwritten. A new processing attempt requires a new document identity.

`needs_review` and `is_reviewed` remain for compatibility. Rejected and expired records keep `needs_review=true` and `is_reviewed=false`. Use `review_status=pending` to query the pending queue. Do not infer approval from these booleans, the presence of results, a missing record, or a polling timeout.

## Read and decide through the API

- [Read current state and decision evidence](/api-reference/get-review)

Reads require `extractions:read`. Decisions require `extractions:write` and access to the document's organization and project. Send `X-Project-ID` when your integration uses an active project. Use the same caller, project, payload, and UUID idempotency key when retrying an uncertain request.

## Historical records

Migration maps previously reviewed records to `legacy_reviewed`; it does not create a new approval event. Historical pending records start their pending age at migration time because their original review request time is unknown. Expiry therefore uses the new `review_requested_at`, not `updated_at`.
